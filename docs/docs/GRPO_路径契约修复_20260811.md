# GRPO 路径契约修复（2026-08-11）——observation 泄漏容器绝对路径

## 1. 一句话结论

SFT 路径泄漏修复后（`/testbed → /workspace`，2026-08-11 上午，见
`docs/SFT_路径泄漏修复与遮挡说明_20260811.md`），GRPO 仍全 0.05 无学习信号。
v15/v16 逐条 rollout 实证定位到**第二个泄漏**：Mac §8 server 的 observation
（bash/search/view_file 输出）**原样透传容器真实工作区绝对路径**
（r2e 镜像 `/home/runner/work/<repo>/<repo>/`，reversal 镜像
`/home/centos/repos/<repo>/`），模型照抄进 str_replace → server 拒绝
（"path must be relative to the task workspace"）→ patch=0 → reward 恒 0.05
→ advantages 恒 0 → 零梯度。

根因：v14 的路径归一化补丁（Mac 侧 vendored LocalDocker）**只覆盖 `/workspace`
前缀**，而容器真实工作区根不是 `/workspace`（bundle 快照自带
GitHub Actions / 构建镜像路径）。

### 3.1 ① Mac observation 归一化补丁规格（转 Mac 侧执行）

**目标**：模型看到的所有 observation 里，容器真实工作区根不再以绝对路径出现。

**位置**：Mac 侧 vendored `environment/server.py` 的 LocalDocker backend——
即 v14 补丁（`_relpath_or_none`）所在处。

**改动**（相对 v14 的 diff 语义）：

```python
# v14: 硬编码只认 /workspace
def _relpath_or_none(path: str) -> str | None:
    PREFIX = "/workspace"
    if path == PREFIX:
        return "."
    if path.startswith(PREFIX + "/"):
        return path[len(PREFIX) + 1 :]
    return None

# v17 规格: 工作区根改为 env 创建时探测到的容器真实根
# 1) create(task_spec) 时记录真实根（容器内执行 `pwd` 或读 bundle 元数据）:
#    r2e bundle    -> /home/runner/work/<repo>/<repo>
#    reversal bundle -> /home/centos/repos/<repo>
#    workspace_root = <容器内探测值>
# 2) 归一化函数接受根参数:
def _relpath_or_none(path: str, workspace_root: str) -> str | None:
    if path == workspace_root:
        return "."
    if path.startswith(workspace_root + "/"):
        return path[len(workspace_root) + 1 :]
    return None
# 3) 渲染 observation 时对全部文本做 workspace_root 前缀替换:
#    obs_text = obs_text.replace(workspace_root, "/workspace")
#    （只替换完整路径段, 防止误伤: 用 regex 边界; bash 输出中唯一确定的
#      前缀替换是安全的——容器根是 env 级常量）
```

**注意**：
- observation 替换范围：bash 输出、search 结果、view_file 内容+错误消息、
  str_replace 错误消息（"path must be relative" 提示里的路径）
- **请求方向**（模型生成 `str_replace path`）继续接受 `/workspace/...` 与相对
  路径（v14 已支持）；归一化后相对路径是首选
- 替换用 regex 边界（`(^|[\s"'()\[\]])`），避免把 `/home/runner/work/aiohttp`
  误伤成别的
- 补丁后必须重启 Mac server（训练中禁止重启 → 重启时机 = v16 停后、v17 启动前）

**验证**（重启后）：`interop_mac.py` 或探测脚本对 r2e-aiohttp 任务
create + bash `pwd` → 返回 `/workspace`（或 `.`），不再返回
`/home/runner/work/aiohttp/aiohttp`。

### 3.2 ② prompt 路径契约（已完成）

`src/sweforge/protocol/system_prompt.py` → `CANONICAL_SYSTEM_PROMPT_VERSION =
"canonical-v3"`：

### 实证链（v15-v19 全版本对比, 跨 205 轮）

| 版本 | clean 轮 | im_end 兑现率 | 关键观察 |
|------|---------|--------------|---------|

| v19 | 0/28 | 0% | view 指引 + v4 fewshot, tools/turns≈4 恒等 |

**核心结论**: 模型**从不生成 `<|im_end|>`**。`stop_token_ids=[im_end]` 注入后
从未触发 -> 每轮生成到 max_tokens（turn_budget 512）被截断 -> "turns" 实际
是截断续写次数 -> 每轮截断文本里恰好 4 个 JSON 被解析（max_calls=4 封顶值）
-> tools/turns≈4 恒等, resp=6144 全顶满（4/6 response_cap）。

### v19 fewshot 为什么没生效（用户提问"fewshot 是否体现 im_end"）

v4 fewshot 是纯散文（`user:/assistant:/tool:` 文本前缀）, 渲染后 Example 块
内**没有任何 im_end token**（模板注入的 3 个 im_end 只是 system/user/assistant
三条消息的边界）。而模型 SFT 学到的真实回合结构是 "JSON 写完 -> `<|im_end|>`
收尾"（SFT 数据 response_ids 每条含 8 次 im_end, 抽样 200/200 条含）——
纯散文示范与该格式完全不对齐, 模型不把它当回合节奏学, 教不会 "1 调用/轮"。

### v20 修复（提示词层, parse 层不动）

1. `system_prompt.py` canonical-v5: fewshot 每条 assistant 回合以字面
   `<|im_end|>` 结尾（`{"command": "cat answer.txt"}}<|im_end|>` 等; tokenizer
   编码为真实 im_end token, 已验证渲染序列含 6 处 im_end 安全）——模型看到
   示范即学会 "JSON 写完 -> im_end 停 -> 等观察" 的真实节奏, stop_token_ids
   才会生效, 每轮回到 SFT 分布（1 调用 + 观察回灌）
2. Rules 明令 "End every response with the <|im_end|> token"
3. view 上下文控制: "Do not re-view line ranges you have already seen"
   （v19 模型 view_file 22-31 次翻页不收敛, 观察回灌吃光上下文）
4. 渲染层 view 行窗口指引保持（serialization.py v5, 整行截断 + start_line/
   end_line 指引）

### v20 观察点（step 1 检查）

- clean 兑现率 > 0（模型开始生成 im_end -> 每轮 1 调用 + 观察回灌）
- tools/turns 从 ~4 回落到 1-2（多调用洪水消失）
- resp 不再全 6144 顶满（模型主动 im_end 收尾而非被截断）
- reward 分化保持 + patch 产出率上升（塑形 v4 持续生效）

## §9 任务多样性截断（2026-08-11, v20 step 1 实证 + v21 修复）

### 现象（用户观察）: "每一步 rollout 的任务都很相似"
v20 step 1 的 8 条 rollout 全是 r2e-aiohttp-430af0af67 / r2e-aiohttp-1770460c4b
两个任务; rl_prompts_train.jsonl 实测只有 2 个 task_id。

### 根因（非未打乱, 是样本截断）:
- `run_grpo_agentic.sh` prepare_grpo 调用 `--max-tasks "${BATCH}"`（batch=2
  → 2 个任务）——GRPO 的 batch 语义是"每 step 采样行数", 不是任务上限;
  42 任务 r2e 池被截到 2 个任务, 模型只见 2 个 aiohttp 任务（v18/v19/v20
  全中招）
- pool 本身无难度排序（r2e-aiohttp-<hash> 文件名序）, seed=7 洗牌取前 2
  是纯随机样本, 不是高难度聚集; 但 2/42 无代表性
- prepare_grpo.py 的 shuffle（seed 确定性）本身正常, 问题在截断点

### 修复（v21）:
- `run_grpo_agentic.sh`: 新增 `--num-tasks`（默认 -1 = 全量 pool 进训练
  jsonl, DataLoader 每 step 采 batch 行轮换, 42 任务约 21 step 轮完一遍;
  val 集保持 BATCH/2+1 固定参考集）
- 同批修复（观测层, 训练中生效）:
  - verl vllm_async_server.py finish_reason 映射保留 "stop"/"length" 区分
    （原全映射 "completed", 丢"模型主动停止" vs "max_tokens 截断"判据;
    vendored 豁免, 先例: flash_attn shim / sft_lora_entry env patch）

    每轮被 max_tokens 截断）, 非判定 bug
